# Будущий PvP: контракт дезертирства

Это проектирование, не реализация сетевой сессии. SteamNetworkingMessages, VirtualGalaxyServer, VirtualClientBackend и ReplayVirtualInstance в PoC не подключаются.

**Решение о состоянии принимает хост правил.** Клиент отправляет только запрос отладки (когда он разрешён хостом), без права самостоятельно назначить состояние чужой части. Хост проверяет аутентифицированного участника, принадлежность матчу, текущего владельца сущности, поколение UID и допустимость перехода.

**Движение выполняет один назначенный исполнитель.** Для исходной модели с владельцем-симулятором это текущий владелец; хост исполняет только собственные/хостовые части. Если будущий сетевой слой изменит модель авторитетности, исполнитель должен назначаться явно. Нельзя выдавать MoveTo одновременно с хоста и клиента владельца.

`StateEvent` уже определён в Core: MatchId, UnitKey (UID + generation), Revision, Sequence, State, OwnerId, Destination, At, Reason. Локальный контроллер создаёт события, которые можно забрать через DrainEvents. Транспорт и применение удалённых событий не реализованы. Временная база будущего протокола — согласованное время матча, а не локальный Stopwatch.

Дополнения к будущему wire-протоколу: ProtocolVersion, AuthorityEpoch, ExecutorId, EventId, RecoveryDeadline и причина отказа. Sequence — порядок потока авторитета, Revision — порядок состояния конкретной сущности. Получатель не применяет чужой MatchId/epoch, старое поколение, дубликаты и убывающие ревизии. Пропуск требует досылки или снимка; он не должен порождать повторную команду движения.

Команда движения получает идемпотентный ключ `(MatchId, AuthorityEpoch, UID, Generation, Revision)`. Исполнитель отмечает принятие до повторных обработок и возвращает подтверждение. Повтор передачи не равен повторному MoveTo. Изменение исполнителя требует отдельной процедуры, чтобы два клиента не считали себя активными одновременно.

Полный снимок после переподключения должен включать состояние, исходного и текущего владельца, исполнителя, цель, фазу пути, ревизию, последнюю принятую команду, время начала/дедлайн восстановления и историю ручной активации текущего PoC. Сначала восстановить сущности, затем правила и ограничения, затем разрешить ввод. Replay одного события без состояния мира недостаточен.

Остальным участникам передавать только разрешённую проекцию статуса. Координаты скрытого противника и его точку отступления не рассылать ради интерфейса. Первая версия планировщика использует заданную точку или свою стартовую зону, а не скрытые данные противника.

Локальный `UserCommandGate` — удобство и контроль ввода, не сетевая защита. Авторитетный обработчик тоже обязан отклонять запрещённый приказ, независимо от UI клиента. Системные корректировки должны иметь доверенное происхождение, которое нельзя указать произвольным полем входящего пакета.

Открытые вопросы: миграция хоста, владение при отключении игрока, единый расчёт стресса, актуальное поколение сущности, порядок восстановления мира и перенос command authority. До их решения нельзя заявлять PvP-готовность.
