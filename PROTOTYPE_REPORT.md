### Независимая логика

Реализован путь `Controlled → Deserting → Retreating → Recovering → Controlled`, а также терминальные для попытки состояния `Destroyed` и `Failed`.

Ручная активация отключена по умолчанию. Проверяются матч, UID/поколение, принадлежность локальному игроку, живое пехотное отделение, положительная численность и конечные координаты. Одновременно контролируется одно отделение. Повторная активация того же ключа в рамках экземпляра контроллера запрещена даже после восстановления — сознательное ограничение PoC против циклических запусков.

Планировщик использует заданную точку или предоставленную стартовую позицию своей команды. Отмена и движение выдаются однократно. Нет смены владельца, удаления отряда, возмещения стоимости, изменения здоровья, стресса или неуязвимости. У контроллера нет API для таких действий.

Подтверждение прибытия требует одновременно статуса пути Arrived и близости к назначенной точке. После фиксированного времени восстановления снимается ограничение управления. В PoC это таймер, не новая модель морали. При неизвестном пути действует конечный тайм-аут; при недостижимой цели, смене владельца, пропаже сущности или ошибке ограничение снимается без бесконечной повторной выдачи приказов. При ошибке ранее запущенное движение не отменяется автоматически.

UserCommandGate фильтрует группу по отдельным сущностям, не затрагивая остальные части. Контроллер выдаёт собственные команды через отдельный интерфейс. Системные и сетевые команды этим gateway не обрабатываются. Это проверено в независимом слое, но ещё не доказано для всех игровых путей ввода.

## Подготовлено

### Входная точка

MelonMod реализует OnInitializeMelon, OnSceneWasInitialized, OnUpdate и OnDeinitializeMelon. Есть собственный префикс логгера, Debug-настройка false, проверка Unity 6000.3.24f1 и SHA256 GameAssembly/UnityPlayer/metadata по исследованной сборке. Совпадение хэшей подтверждает только идентичность сборки, а не исправность адаптера.

При неизвестной версии или исключении функциональность отключается. Между сценами контроллер и выбранный объект сбрасываются. Подготовлены `AttachReadOnlySession` и `DebugActivate`: первый принимает будущий provider своей сессии, второй выполняет только разрешённый ручной запрос. Автоматической вероятности дезертирства и горячих клавиш нет.

**Текущая DLL сама не обнаруживает подразделения и не привязывает игровую сессию.** Без provider она только выполняет lifecycle/диагностику совместимости. Даже после прикрепления provider ExperimentalGamePort.ReadyForControl остаётся false, поэтому DebugActivate не запустит движение. Это явный предохранитель непроверенной интеграции, а не «рабочее дезертирство в игре».

### Диагностика и движения

Код чтения подготовлен для LuaUnit, UnitComponent, InfantryUnitComponent, StressComponent и CommandsComponent. Он возвращает UID, тип части, владельца, координаты, численность, стресс/максимум/уровень и тип текущего приказа. Владелец проверяется до чтения позиции; компоненты копируются только в DTO для чтения. Стресс не изменяется.

Подготовлены вызовы LuaUnit.StopAllCommands и MoveTo с attackMove=false. Исследованы альтернативные EntitiesHelper.CancelCommand/CreateMoveCommand и MoveToPositionCommand. Вызовов ReturnToBase нет.

Для Harmony подготовлен выключенный CandidateOrderHook на индивидуальный AddCommandsQuery. В дампе подтверждён переход из группового UpdateCommandsQuery в этот метод. Общий setter CurrentCommand и входящие NetworkCommandService не перехватываются. Детальные сигнатуры, аргументы и ограничения: [GAME_INTEGRATION.md](docs/GAME_INTEGRATION.md).

### Будущий PvP

В Core уже есть события с идентификатором матча, ключом части, ревизией и порядком. Документ [PVP_DESIGN.md](docs/PVP_DESIGN.md) определяет хост принятия решений, единственного исполнителя движения, подтверждения, дедупликацию, проверку владельца и состав снимка для переподключения. Сетевой транспорт, лобби и применение удалённых событий не реализованы.

2. Проверить поддержку данной Unity/IL2CPP-сборки выбранной версией MelonLoader. При несовместимости остановиться; обход защитных подсистем не входит в работу.
3. Только в тестовой среде подготовить загрузчик по его официальной инструкции. Помнить, что сам загрузчик создаёт логи/обёртки в своём окружении.
4. Для lifecycle smoke-test разместить `DynamicFrontline.MelonLoader.dll` в тестовом Mods, а Core/GameAdapter — в тестовом UserLibs. 6. После получения обёрток реализовать provider и сначала проверить только чтение одного своего пехотного отделения. Сравнить численность/стресс/приказ с наблюдаемым состоянием; подтвердить отсутствие чтения противника.

Проверить физическое движение, уязвимость, одиночный/групповой ввод, гибель и возврат управления. Официальный PvP на этом этапе не использовать.

Ближайшее действие — проверка реальных обёрток и read-only provider, затем командного пути. Остальные механики Dynamic Frontline в этот этап не добавлялись.
